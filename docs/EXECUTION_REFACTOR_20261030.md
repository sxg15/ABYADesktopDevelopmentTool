# 工作流 2.11 执行重构

用户已批准交付优先、验证方法可替换、普通故障自动恢复、归因需要证据的方案。
现有任务继续固定原 policy；本次不热迁移正在执行的“大鱼吃小鱼”。

## 实施与验收

1. 单工作项恢复：普通失败在原 ID 内复核假设、换方法、复验，不派生 repair-plan/handoff-repair 链。
2. 观察与归因分开：未测、验证不可用、验证失败、功能失败独立记录；外部标签不能证明平台故障。
3. 有界结束：用户暂停、未知写入、权限条件、无进展与已完成分别记录；耗尽后形成内部技术队列及成果清单。
4. 验收范围：检查绑定已批准需求/计划和可观察结果，额外可选检查不自动制造门槛；严重功能问题仍须处理。
5. 可玩预览：已验证核心包可在 Lua 阶段预览，不改变正式试玩和人工验收门槛。
6. 平台基线：完整构建指纹、已发现能力及实际测试范围形成可复用基线；基线不证明所有功能无缺陷。
7. 测试执行器：分类明确拒绝/断连/断言失败；未知写入不重放，读取可有界恢复，实际结果可复核。
8. 替换提示与 Skill：新策略使用统一短契约；旧协议按需参考，不重复注入历史版本规则。

## 发布条件

- 聚焦回归和完整工程检查通过；未知写入、用户暂停、审批与旧策略兼容性必须保留。
- 原生执行验证必须证明自主运行，不把协调窗口手工制作或测试夹具结果记成自动游戏通过。
- 代表性游戏覆盖大小记忆、大鱼吃小鱼以及一笔画/见缝插针；重复测试并注入断连、错误参数、旧快照、错误阻塞判断。
- 报告首次可玩包、主动执行、验证、恢复、人工等待和总历时，保留失败运行。
- 3–4 小时是有明确规模的实测目标，不是单测或提示词检查可以证明的结论。
- 候选未通过真实任务验证前不替换正式 Publish；旧任务、存档、审批、成果和累计耗时不重置。
