# 工作流首轮测试修复记录

本轮把需求问答改为 APP 弹窗，完成明确人数模式、持久草稿和答案修订、原会话恢复、授权更新、历史关联修复与定位信息。完整游戏制作流程和三个文档确认点沿用。

## 核心变化

- 新任务人数默认“未明确”。允许提问时让策划选择；已有明确意图直接沿用。不追问时在需求文档中列出假设。
- 发布问题后，当前任务即使在终端页也能弹出问答。上一题、下一题、查看全部、自动保存、稍后回答、重新打开与修改已提交答案均已接入。
- 用户答题走 APP 专用接口，CLI 只能发布问题和读取状态，不能代答或批准文档。
- 暂停会中断原生执行并关闭该对话后端，再撤销授权；继续用原生 ID 和新授权恢复。各对话使用独立执行后端，元数据查询使用另一后端。
- 已分配的新原生 ID 在后续 RPC 前保存，准备失败不静默回退为新会话；新 APP 对话也不能自动继承同目录旧历史。
- 旧记录存在歧义时人工选择同目录候选；修复备份元数据和旧活动投影，两条原生历史不合并、不删除。
- Codex 问答续接验证原始会话与答案版本，通过原生接口开始新轮，并用持久回执阻止重复发送。未知结果不自动重放。
- 会话信息页提供精确 ID、目录、用时明细和最近原生 Token 总量；不承诺自动进入 Codex 桌面侧栏。

原始调研与错误关联分别位于两个真实原生会话，这一点已核对。导致本次分裂的原始启动时序尚未完整复现，不能把某条猜测当作唯一根因。已移除静默替代会话的路径并加入后续诊断。

暂停与恢复采用独立后端，是因为取消订阅不等于立即释放执行上下文。当前协议说明会保留无订阅会话一段时间，恢复时不能依赖它已经卸载。[OpenAI app-server 文档](https://learn.chatgpt.com/docs/app-server)

## 仍需实测的范围

策划需用实际需求跑完整任务，验证原生权限弹窗、长期运行和游戏质量。原生 ID、问答和授权测试不算 8＋4 的游戏测试轮次。
计时提供真实明细，暂不声称能精确区分模型计算、工具等待、人工权限等待及所有异常停顿。重叠区间不可直接相加；缺失数据标为不可用。
Codex 桌面能否展示通过 CLI 注册的项目仍依赖客户端能力，本轮提供准确关联和查找信息，没有操作它的内部数据库。
