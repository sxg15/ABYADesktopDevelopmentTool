# 首轮工作流测试问题修复执行计划

日期：2026-10-08  
状态：核心修复及 APP 问答弹窗已实现，开发侧回归已通过；独立测试包准备交付。原测试任务已备份并准备恢复说明，因旧 APP 仍运行，实际关联修复与完整玩法验收留待切换新版后完成。

执行记录与限制见 [测试说明](WORKFLOW_RECOVERY_TEST_GUIDE_20261008.md)。本计划中的细项以该说明记录的实际验证范围为准：已提供计时明细与原生用量快照，精确等待分类仍需试点校准；不把框架联调当作完整玩法验收。

## 1. 这次要做到什么

让策划能从需求输入开始，方便地回答和修改问题；中断后可以回到原任务继续；需要排查时，能准确找到对应的 Codex 会话。先修复这些基础问题，再继续“堵猫咪”的完整玩法测试。

首轮范围包括四件事：玩法人数不再被默认为多人、在 APP 内回答需求问题、可靠恢复原会话与工具权限、显示准确的 Codex 会话信息。暂不重做整套聊天界面，也不新增美术制作流程。

沿用已经确定的流程：需求文档、执行计划、最终交付由策划确认，其余正常步骤自动推进；必要工具或素材缺失时明确暂停。试点仍完整执行 8＋4，但要等会话和交互修复后再测。

## 2. 已查明的问题与需要验证的部分

| 问题 | 已有证据 | 本次处理方向 |
| --- | --- | --- |
| 一开始直接问多人玩法 | 测试提示词带有“联机小游戏”线索；现有生产记录没有独立的单人/多人字段 | 区分明确决定和参考线索，未明确时让策划选择 |
| CLI 答题难修改 | 当前主要通过终端转发键盘输入，没有 APP 自己保存的答题表单 | 增加需求问答面板，保存草稿并支持回看修改 |
| 继续后像是历史丢失 | 原始调研和后续纠正分别在两个原生会话中，APP 关联的是后者 | 修复原生会话绑定与恢复，避免静默创建另一条会话 |
| 继续后工具不可用 | 日志出现 ABYA 的 `session_unauthorized`；这是工具会话授权错误 | 恢复时更新实际执行工具的上下文，并验证权限可用 |
| Codex 中找不到对应聊天 | 原始调研会话未正确关联命名；历史侧栏分组不保证自动收纳新会话 | 正确关联后显示名称、ID、路径与定位状态 |

历史尚在，不应把这次问题直接定性为“Codex 删除了对话”。还需要复现两点：到底哪个启动或回退分支创建了第二条会话；旧的 ABYA 授权具体残留在哪一层。修复前先定位，不能只靠延长有效期掩盖问题。

## 3. 执行顺序与交付物

按以下顺序推进，每阶段通过验证后再接下一阶段。不需要策划逐项确认技术细节；需要策划参与的是修复后的体验验收。

| 阶段 | 工作 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| P0 | 备份现场、补充诊断、复现 | 复现记录、会话映射、故障触发路径 | 能区分绑定错误、权限错误、终端断开 |
| P1 | 修复会话绑定、暂停与恢复 | 稳定的原会话恢复、权限续接、明确按钮语义 | 中断后同一原生 ID、历史和工具都正常 |
| P2 | 补齐单人/多人需求入口 | 需求字段、提问规则、文档同步 | 明确选择被沿用，未明确不会暗中默认 |
| P3 | 实现 APP 需求问答面板 | 可回看修改的表单、草稿、提交与恢复 | 关闭或重启后答案仍在，提交不重复 |
| P4 | 完善 Codex 会话定位 | 会话信息卡、受支持的打开或查找入口 | 定位到实际执行会话，不只是同名记录 |
| P5 | 回归、打包、试点复测 | 测试记录、隔离测试包、使用说明 | 开发侧验证通过后交给策划跑完整任务 |

### P0：保留现场并锁定故障路径

1. 备份本次任务的 APP 会话元数据和生产记录，记录程序版本、Codex CLI 版本与工作目录。诊断文件不包含令牌或连接密钥。
2. 通过受支持的只读接口核对两个原生会话，记录 APP 会话 ID、原生会话 ID、启动方式、恢复结果、回退原因及时间。
3. 用临时测试任务复现“首次启动 → 回答问题 → 停止终端 → 继续”，分别检查终端进程、原生 turn 和 ABYA 工具授权的状态。
4. 检查安装版本的 app-server 协议与请求归属，确认当前版本支持的中断、恢复、输入请求和上下文更新方式。

验收：能给出导致两个原生会话出现的调用链；若无法复现，明确列出证据缺口并保留诊断，不把猜测写成结论。

### P1：优先修复“停了以后还能可靠继续”

**会话绑定**

- 每个 APP 对话保留稳定的原生会话 ID，开始接受用户输入前验证实际连接的会话与记录一致。
- 已知原生 ID 的恢复失败时，显示失败原因和修复入口，不静默切换成新会话。
- 旧数据恢复如果出现多个候选，按明确的启动记录核对；不能只取同目录最新或最早的会话。
- 恢复订阅与历史成功前，不清空现有界面记录。终端显示缓存、原生对话历史与生产文档分别管理。

**按钮与运行状态**

| 操作 | 预期行为 |
| --- | --- |
| 暂停 AI | 中断当前原生执行，等待状态确认；保留历史、需求草稿和任务记录 |
| 继续原会话 | 恢复同一个原生 ID，校验工具权限，再允许继续执行 |
| 收起终端 | 只关闭显示区域；若后台运行，明确显示“后台执行中” |
| 修复连接 | 修复连接或工具授权，不创建新对话、不清空历史 |
| 刷新会话列表 | 只更新列表，不重启执行；与上述按钮使用不同名称和提示 |

**权限恢复**

- 将授权有效期、服务重启、主动撤销区分记录；不把所有错误显示为“对话过期”。
- 恢复时刷新绑定到当前任务和会话的授权，并应用到模型实际执行工具的上下文。
- 用实际执行上下文中的只读检查验证恢复；仅测试 APP 临时启动的子进程不算通过。
- 若已加载上下文不能直接更新，按当前协议采用该会话的受控重载与恢复；不能随意重启共享服务影响其他任务。
- 明确暂停、终端断开、后台继续各自的授权生命周期；不允许后台仍执行却立即撤销它需要的权限。
- 工具写入返回结果未知时先核对结果，不能因重连而自动重放写入。

验收：真实 CLI 中完成中断和恢复；原生 ID 不变，历史可读，工具检查正常；故障时停在可理解的错误状态，原数据保留。

### P2：把单人/多人作为明确的需求决定

1. 增加玩法人数模式：未明确、单人、多人。与“允许提问/不追问”和任务类型分别保存；多人也不直接等于联网。
2. 用户已经明确说明时直接沿用，不重复询问。截图栏目、素材名称、模板默认值只作为线索，不能直接当成用户决定。
3. 允许提问且尚未明确时，优先问单人还是多人；选多人后，再按需要问协作、对抗、是否联网及人数。
4. 不追问模式下，在需求文档中明确列出假设及影响，在既有需求确认环节敲定，不增加额外确认关卡。
5. 修改选择时同步相关问题和需求文档。已经确认的需求如发生实质变化，沿用版本与失效机制重新确认受影响的内容。

验收：显式单人、显式多人、没有说明、仅截图暗示联机四类输入均正确处理；需求记录与文档内容一致。

### P3：让策划在 APP 中完成需求问答

首版采用 APP 自己管理的需求问答面板，终端继续负责显示执行过程。优先通过现有桌面 CLI 扩展持久化的业务问答接口，避免一开始就替换完整的 Codex 客户端。

**策划看到的交互**

- 顶部显示“需求梳理 · 第几组问题”，标明已回答和待回答数量。
- 每题支持选项和自由补充；可以点“上一题”“下一题”或直接切换题目。
- 自动保存未提交的答案；提供“查看全部答案”和“提交本组答案”。默认选项不会自动发送。
- 提交前随时修改；提交后用“修改已提交答案”产生新的答案版本，保留旧记录，并标记受影响的问题。
- 不追问任务不弹出额外业务问答；必要安全或敏感操作确认仍走原有机制。
- 回答问题只代表提供需求信息，不代表批准需求文档或执行计划。

**数据和执行约束**

- 问题组保存稳定 ID、版本、题目与选项、草稿、已提交答案、提交时间，以及任务、APP 对话、原生会话的关联。
- 数据写入现有持久化体系，支持未提交、已提交、已替代、已取消等明确状态；刷新或重启不得丢草稿。
- 提交操作具有去重标识，避免重复点击、重连或事件重放让 AI 收到两遍答案。
- 后续回复必须回到正确的原生会话。具体续接方式在 P0 验证后确定，不仅依赖模拟键盘输入。
- 中断导致原生输入请求失效时，保留业务问题与答案；重建有效请求后续接，不能向失效请求 ID 提交。
- 原生 `requestUserInput` 接入单独验证请求归属；同一问题只能有一个提交入口，不能让远程终端和 APP 同时回答。
- 更新玩法工作流 Skill，让需求阶段使用面板接口；只读取当前阶段必要资料，不增加重复检查或无意义确认。

验收：回答第一题后返回修改、查看整组答案、提交后纠正、答题中暂停、关闭 APP 后恢复全部成功；答案只提交一次。

### P4：让会话可定位、状态说得清楚

1. 在任务中展示实际原生会话的名称、ID、工作目录、关联状态和最近连接结果；原生会话没有名称时明确显示，而不是伪造关联成功。
2. 基于正确绑定同步名称和项目元数据，区分“原生关联成功”与“Codex 桌面能否直接打开”。
3. 核对当前主机和 Codex 数据根目录是否一致，不读取或展示登录凭据。
4. 如果当前 Codex 版本提供受支持的打开方式，接入直接打开；否则提供复制会话 ID、精确工作目录和查找指引，并实测有效性。不写入 Codex 内部数据库，不依赖未经验证的深链。
5. 不承诺新对话自动进入历史的“ABYA 开发”侧栏分组。查看历史与在 Codex 外部继续执行分别说明；后者需要有效 ABYA 上下文和同一时刻只有一个入口提交执行指令。

验收：新建、暂停恢复、APP 重启后，信息卡均指向实际执行会话；若当前 Codex 桌面无法定位，明确显示兼容性限制，不能报告已完成自动定位。

## 6. P5：回归与发布条件

### 开发侧测试矩阵

| 场景 | 通过标准 |
| --- | --- |
| 单人/多人已明确或未明确 | 明确意图直接沿用；未明确可选择；参考线索不替代决定 |
| 不追问模式 | 假设在需求文档中可见，通过原有确认入口敲定 |
| 提交前返回上一题修改 | 答案保留，最终提交为修改后的版本 |
| 提交后改答案 | 旧版本可查，受影响内容更新，无重复提交 |
| 答题中暂停或关闭 APP | 问题和草稿可恢复；失效请求不会被错误回答 |
| 执行中暂停再继续 | 当前执行确实停止；继续仍是同一原生会话 |
| 只收起终端 | 后台运行状态准确，所需授权不会被误撤销 |
| 授权过期或桌面服务重启 | 恢复实际工具上下文；只读权限检查成功后才能继续 |
| 原生会话恢复失败 | 保留原 ID 和历史，显示原因，不静默新建会话 |
| 两个任务同时运行 | 恢复其中一个不破坏另一个，权限不能跨任务使用 |
| 工具写入时连接断开 | 先核对执行结果，不能直接重放造成重复写入 |
| 查找 Codex 会话 | 显示实际 ID；验证支持的定位方式，限制如实说明 |
| 归档与已有生产确认 | 原有归档、三次文档确认和版本失效机制无回归 |

验证分三层：状态与持久化的单元/组件测试；协议故障模拟；安装版本 Codex 的真实生命周期联调。授权过期可通过可控测试时钟验证，无需等待十二小时。真实联调用独立临时任务，不让故障注入影响现有任务。

按仓库要求完成前端检查、Rust 格式检查、Clippy 和 Rust 测试，并执行受影响的 CLI/Skill 检查。单元测试通过不能替代真实 CLI 的中断、恢复和问答验证。

### 时间与效果记录

- 分别记录总历时、AI 活跃时间、人工答题/确认等待、暂停时间、故障与重连耗时。并行事件按时间区间去重，口径写在报告里。
- 记录提问组数、答案修改次数、三类人工确认次数、恢复成功率、错误新建会话次数、工具授权失败次数。
- 每轮迭代保存开始和结束时间、发现的问题、修改内容、验证证据及未解决事项。
- Token 只采集原生接口实际提供的用量；拿不到就写“不可用”，不推算。终端重放和跨会话恢复不能重复累计。
- 本次已发生的故障单独记为需求阶段集成问题；不能拿它的总耗时当作完整玩法制作效率。

### 交付给策划的内容

1. 隔离的测试安装包，避免覆盖正在使用的正常版本；附版本、运行入口和回退办法。
2. 一页测试说明：怎么开始、怎么改答案、怎么暂停和继续、怎么定位会话、问题在哪里反馈。
3. 开发侧测试报告，以及本次旧任务恢复记录。
4. 两条试跑路线：先用现有任务验证恢复，再建干净任务从需求开始验证全流程；最后完成玩法执行、8＋4 与人工验收。

发布门槛：不得出现恢复到错误会话、丢失已保存答案、重复提交或跨任务使用权限。无法恢复时必须保留数据并明确报错。Codex 桌面定位能力如存在版本限制，必须在交付说明中写明，不能掩盖为“已支持”。

## 7. 范围和实施安排

建议按四个可独立检查的改动批次提交：①诊断、会话和权限；②人数模式、问答数据与 CLI；③问答界面与会话定位；④回归、文档和测试包。每批保持代码、契约与 Skill 同步，不等到最后统一补说明。

P1 是阻断问题，应先完成真实联调再扩展 UI。P3 的工作量取决于 P0 查明的当前协议与输入请求归属；调查完成后再给出可靠工期，不预先承诺固定天数。首轮目标是尽早提供能稳定试跑的版本，不扩展到完整聊天客户端或自动侧栏管理。

安全边界保持不变：不取消授权校验，不持久化明文能力令牌，不通过延长到永久有效修复续接，不增加无意义确认；敏感操作确认与必要测试保留。
