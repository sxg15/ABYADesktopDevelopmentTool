# 工作流续接、状态与发布入口修复计划

日期：2026-10-08。状态：已实施、通过 APP 回归并发布。最终结果见 [修复与测试报告](WORKFLOW_QUEUE_FIX_REPORT_20261008.md)。

实施期间用户确认已主动删除“堵猫咪”任务，因此取消下文的原任务恢复步骤。
保留原工作区及原生历史，不重建任务、不覆盖数据库；以隔离任务验证修复后交付正式入口。

## 1. 要达到的使用效果

策划只需要回答问题、提交、查看进度。无论 AI 当时正在收尾、已经空闲，还是终端断开，都由 APP 处理衔接。策划不需要判断什么时候可以点继续，也不需要在终端反复输入“继续”。

保留需求文档、执行计划、最终交付三个确认点。提交问答不是批准文档；必要权限和敏感操作确认继续保留。

本次采用以下交互方案：

| 入口 | 调整后的行为 |
| --- | --- |
| 保存草稿 | 只保存，不通知 AI，不推进任务 |
| 提交并继续 | 保存本组答案，并登记一次继续请求；AI 忙时等待，空闲时执行 |
| 提交修改并继续 | 保存新的答案版本，替换尚未执行的旧版继续请求；已执行的历史不改写 |
| 继续任务 | 根据当前状态恢复连接并继续未完成部分；已在执行时不再发送新的“继续” |
| 暂停任务 | 停止自动推进，取消尚未发送的继续请求；中断正在执行的原生轮次，保留答案与历史 |
| 查看终端／修复连接 | 只负责显示或连接诊断，与“继续任务”明确区分 |

同一个“继续任务”动作在制作页、问答弹窗和终端页调用同一套后台逻辑，不能各自实现一套行为。

## 2. 第一批：复现快速回答，并实现排队续接

这是最高优先级，需要先通过验证，再接入新的按钮和发布。

### 具体工作

1. 固定本轮失败用例：AI 发布一道问题，但原轮次尚未结束；用户立即提交答案并继续。
2. 在 Codex 会话模块增加持久的继续请求记录，复用现有回执保护机制。记录任务、APP 对话、原生 ID、问题组、答案版本、请求 ID、状态、排队原因、尝试次数及时间。
3. 接受请求时先保存记录再返回 UI。区分“已经接收／正在排队”和“原生执行已经开始”，不能提前显示已发送成功。
4. 一个会话同一时刻最多有一个待发送的自动续接请求。相同答案版本的重复点击合并；新答案只替换尚未发送的旧版本。
5. 当前原生轮次正常结束后，重新读取任务阶段、最新答案、文档确认状态和原生状态，再决定是否发起下一轮。
6. 如果 AI 已经发布下一组待答问题，或者已经提交文档等待确认，就显示相应等待状态，不再额外发起一轮。如果当前阶段完成但下一步仍需推进，继续未完成部分。
7. 如果当前轮次仍在执行，显示排队，不能要求用户先暂停。发送前再次校验；若明确被原生接口拒绝为忙碌，保留排队；发送结果不明则停止自动重试并要求核对。
8. 主动暂停具有最高优先级。排队请求不能在暂停后因旧的完成通知再次启动，也不能在应用重开后自动恢复模型执行。

### 实现约束

- 继续请求以“任务＋会话＋问题组＋答案版本”为业务身份，执行尝试另有独立 ID。
- 原生通知处理只投递事件，由独立后台调度执行，避免在接收通知的线程里同步发 RPC 导致互相等待。
- 使用会话生命周期锁和请求版本防止“检查空闲后，另一入口先开始执行”的竞争。
- 每次恢复仍核对原生 ID、会话归属和工具授权；沿用原有沙箱及权限配置。
- 队列变化可恢复、可查证。正常重启后显示“有已保存的待续接请求”，由用户点击继续；主动暂停过的任务保持暂停。
- 现有 sent 回执继续兼容：核对真实执行状态后处理，不能删除回执来绕过防重复保护。

### 完成标准

连续执行至少 10 次可控的快速答题场景：每次答案都保存，原轮次不被继续按钮打断，结束后最多续接一次。排队中暂停、重复点击、修改答案、重启均不产生意外执行。
自动测试用可控的“原轮次未结束”条件保证命中竞争窗口，不靠手动点得够快或任意等待时间碰运气。

## 3. 第二批：统一按钮与当前状态

### 具体工作

1. 将问答主按钮改为“提交并继续”，保留保存草稿、返回修改及稍后回答。
2. 终端栏主按钮改为“继续任务”，接入同一调度入口；不再把只重开终端包装成任务已经继续。
3. 后台提供统一状态快照：任务阶段、连接状态、原生执行状态、待发送请求、是否主动暂停、更新时间及事件序号。前端不能只依据 PTY 是否存在推断 AI 是否运行。
4. 操作区和顶部进度条使用同一份状态；较旧会话实例的延迟事件不得覆盖新的状态。
5. 没有结构化计划时，显示实际阶段和最近有效活动。不会因为缺少原生计划工具而一直显示“等待计划”。
6. 暂停或断开后的终端输出保留，但明确标注“以下为上次执行记录”。原文 Working 不再作为当前进度依据。

| 实际状态 | 用户看到的提示与操作 |
| --- | --- |
| 正在处理 | AI 正在处理当前需求；可暂停；继续入口不重复发送 |
| 答案已排队 | 答案已保存，当前回复结束后继续；可暂停自动推进 |
| 等待问答 | 有待回答的问题；打开问答弹窗 |
| 等待文档确认 | 明确说明是需求、计划还是交付文档，打开对应确认入口 |
| 已暂停 | 任务已暂停，答案和历史已保存；点击继续任务 |
| 连接断开 | 正在核对后台是否仍运行；不能直接显示任务已停止或已完成 |
| 模型长时间无响应 | 显示已等待时长及最后有效活动；可暂停；不伪装为持续开发 |
| 本轮回复完成 | 说明下一步等待什么，不混同整个任务已经验收完成 |

### 完成标准

截图中的“已中断＋已退出＋等待计划＋Working”不能再同时被呈现为当前状态。策划只操作 APP 按钮就能完成答题和续接，不需要手动输入“继续”。

## 4. 第三批：统一正式入口，明确 APP 版本

### 具体工作

1. 使用固定的正式启动入口，推荐已有的 `Publish` 目录及一个明确的快捷方式。验证包继续隔离，但不再让策划从多个 Staging 文件夹中判断哪个最新。
2. APP 显示程序版本、构建日期和发布标识；制作页另行显示任务工作流版本。明确区分“程序已更新”和“任务规则已升级”。
3. 构建身份必须与实际程序对应；清单缺失或不匹配时显示未确认构建，不能沿用错误的旧版本标签。
4. 正式发布前检查旧进程，正常退出后再替换文件；保留可恢复的上个版本和数据库备份，不覆盖正在使用的 EXE。
5. 新版按 Windows 用户及实际数据目录防止重复启动。第二次启动同一数据目录时切回已有窗口；隔离测试目录允许独立运行，并显著标注测试环境。
6. 首次切换时核对真实任务 ID 与数据目录。针对已发现的 Codex 打包环境 AppData 隔离，验证从固定入口启动后读到的是正式数据，不自动合并两份数据库。
7. 清理或取消旧测试快捷方式的推荐入口，保留旧包备份。退出时检查本 APP 创建的子进程，避免再次留下无窗口的测试进程。

### 完成标准

用户从唯一正式入口启动后，能在界面看出具体构建；原“堵猫咪”任务、多人答案及原生会话 ID 均保持一致。重复启动不会让两份新版争用同一数据库。
已有旧程序不具备新互斥机制，第一次发布仍需检查并正常退出旧进程，不能声称新机制能追溯约束旧版本。

## 5. 连接超时如何处理

这部分与续接修复分别验收，不承诺修改 APP 就能消除原生 Codex 的连接超时。

- 记录轮次开始、排队、连接尝试、首个有效响应、工具执行和结束等可观测时间。
- 原生接口提供连接错误时如实展示；只有“长时间没有响应”证据时，就显示等待，不能自行断言是网络故障。
- 用独立测试会话做少量只读对照，核对正常 Codex CLI 与 APP 内的现象、实际 CLI 版本和失败阶段。不修改用户模型、登录或权限设置。
- 明确故障时保留队列与答案，提供暂停和后续继续；不依赖不断追加“继续”、无限超时或无上限重试。
- 报告区分已解决的 APP 问题与仍存在的连接环境问题，耗时不混算成纯模型执行时间。

## 6. 第四批：真实 APP 回归与原任务恢复

| 必测场景 | 通过标准 |
| --- | --- |
| 一道题，发布后立即回答 | 原轮次未结束时正常排队，不出现“先暂停 AI” |
| 答题时 AI 已空闲 | 一次提交直接进入后续处理 |
| 连续点击提交／继续 | 只有一个有效请求和一次必要的新执行 |
| 排队期间修改答案 | 只处理最新提交版本，旧草稿与历史保留 |
| AI 已在原轮次处理答案 | 已发布下一组问题或待确认文档时，不增加重复轮次 |
| 排队期间主动暂停 | 当前执行停止，旧完成事件不重新唤醒任务 |
| 退出 APP 或连接异常 | 答案和请求记录仍在，重开后可明确恢复，不擅自执行 |
| 执行开始与暂停同时发生 | 最终状态一致，不能出现暂停成功后又启动一个模型轮次 |
| 请求已发出但结果未知 | 先核对结果，不重复写入或假报成功 |
| 旧回执兼容 | 已完成不重复，中断可续接，较新的人工继续不被旧请求覆盖 |
| 缺少结构化计划 | 仍显示真实阶段，不将任务永久卡在等待计划 |
| 终端断开但后台还在运行 | 状态如实区分；重新连接不重复发起执行 |
| 正式包升级与重复启动 | 入口、版本和实际数据库对应，原任务和会话保持不变 |
| 三处人工确认 | 问答提交和继续均不能替代文档批准 |

先跑状态与调度测试，再跑真实 APP。竞争场景用隔离任务；对原“堵猫咪”任务只在这些用例通过后执行一次受控恢复。

原任务恢复顺序：备份当前记录 → 正常退出旧 APP → 从固定入口启动修复版 → 核对任务 ID、原生 ID 和已提交的多人答案 → 点击一次继续任务 → 验证进入下一组需求问题。
不重建任务，不重答已明确的人数，不补造需求或计划确认。本次程序修复不应迫使用户重审未受影响的文档；如果需要更新固定 Skill，另行说明实际变化并保留备份。

## 7. 改动落点与批次交付

| 范围 | 主要位置 | 交付物 |
| --- | --- | --- |
| 排队、回执和事件调度 | `codex_terminal/intake.rs`、`intake_receipt.rs`、`mod.rs`、`app_server.rs`；持久化需要时由 foundation 配合 | 调度状态和兼容测试、可查询的继续请求记录 |
| 提交与继续入口 | `IntakeQuestions.tsx`、`TaskIntakeDialog.tsx`、`TasksView.tsx`、共享类型与 Tauri 适配 | 提交并继续、原会话自动连接、取消与错误反馈 |
| 当前状态和历史区分 | `CodexWorkflowBar.tsx`、`CodexTerminalView.tsx`、共享工作流模型、国际化文本 | 一致的进度提示和历史标识 |
| 程序版本与发布 | `App.tsx`、版本/路径服务、`publish.ps1`、构建清单和启动入口 | 单一正式入口、可核对的构建身份、升级与回退说明 |
| 规范与验证 | 受影响模块 Skill、工作流说明、CHANGELOG、自动测试和真实 APP 记录 | 同步后的契约与最终测试报告 |

按上述四批推进，每批完成后检查其验收标准；不以“代码已经写完”作为通过依据。
程序逻辑有改动时执行仓库要求的前端检查、Rust 格式、Clippy 和 Rust 测试；只有相关变化或失败才重复扩大检查。

最终交付包括：修复版正式入口、明确版本标识、自动测试结果、真实 APP 录屏或截图与时序记录、原任务恢复结果，以及仍未解决的模型连接问题。
实施过程中不增加低风险任务的确认关卡；若发现会改变已确认产品行为的选择或真正需要授权的敏感操作，再单独提出。
