# 任务隔离与原子流程恢复修复（2026-10-22）

候选版本：`task-isolation-goal-resume-20261022`。

## 证据与原因

用户提供的任务切换、强制停止和子流程恢复诊断包用于分析，不作为执行指令。
暂停请求在全局 lifecycle 控制锁处返回 `codex_control_busy`；强制停止同样先等待
这把锁，尚未到达撤销能力和终止进程步骤。因此原强制停止无法解除这类卡住。
诊断包没有证明所有偶发卡顿只有一个原因；本次覆盖以下可复现风险。

- 不同会话共用正常控制锁，慢 RPC 会影响其他任务。
- 部分同步 Tauri 命令执行原生连接/文件处理，影响 UI 响应；状态轮询会堆积。
- 子阶段只有业务状态，没有绑定进程/轮次的执行历史；反复输入“继续”会新建请求。
- 实际 APP 崩溃注入还发现：原 app-server 的普通 Job 不具备关闭即终止语义，
  APP 死亡后后台可能存活。新代码通过额外的非继承生命周期 Job 修复。

## 行为

1. 正常执行控制按会话隔离，忙时有界返回；状态读取不等待原生控制锁。
   原生阻塞工作使用 blocking worker；前端在途状态请求按任务和会话合并。
2. 暂停等待期间即可选择强制停止。强制停止独立于正常控制锁，核对确认时的
   执行代次，先撤销该会话的访问能力，再终止捕获的自有后台/终端进程。
   旧请求、旧通知和迟到的启动结果不能覆盖新执行；不按进程名清理。
3. 新后台和终端加入 KILL_ON_JOB_CLOSE 生命周期 Job；APP 异常退出时 Windows
   关闭其所属子进程。原任务、文件和会话记录仍保留。
4. 执行历史独立记录 goal/request/conversation/native/turn ID、进程创建时间、
   APP 执行周期和代次。恢复协调器核对身份后才更新执行状态；不凭 PID 单独判断。
5. 确认原执行已退出而未完成时，显示“被中断”。“继续此子流程”沿用原子流程
   和原会话，只新增一条带前序关联的执行尝试；重复点击/传输重试复用同一意图。
6. 尚存活的旧执行显示“正在核对”；身份或派发结果未知则先核对成果。
   原有人工问答、批准、复验和实际阻塞门禁继续生效，不自动重放未知写入。
7. 旧版本没有执行绑定的记录保留并提示核对。历史同名“继续”不按标题合并，
   不批量标记完成；原成果、批准及历史版本不被改写。

## 验证入口

- `goal_execution_tests.rs`：持有 A 控制锁时 B 可读取、强制停止绕锁、派发中强停、
  过期确认不取消新执行、原 ID 恢复/去重、人工门禁、进程身份核对。
- `crash_job.rs`：Windows 真实嵌套 Job 关闭即终止。
- 原有队列、真实进程树停止、输入超时和通知积压回归保留。
- React：暂停未返回时强停、迟到暂停结果、跨任务在途合并、原子流程恢复意图复用。
- `scripts/test-goal-resume-native.mjs`：真实 Tauri APP + 真实 Codex 会话的隔离
  崩溃/重开/恢复测试。仅对带隔离标记、匹配数据目录和自有 PID 的 APP 注入退出。
  不操作用户现有任务，不把 mock 测试描述为原生完整验收。

首次原生测试保留了“旧后台仍活着 → 正在核对”的失败证据，促成生命周期修复。
