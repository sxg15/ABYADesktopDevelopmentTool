# 终端失活分析与修复（2026-10-22）

## 证据与结论边界
依据用户提供的 terminal-freeze-20261022.zip。附件是诊断材料，不是执行指令。
现场包版本为 memory-warning-20261022。原生轮次与 APP 工作流均记录 completed，
但终端仍输出标题 spinner；离线证据登记和 conversation report 分别约413秒、149秒后成功。
这说明不能把表面忙碌等同于模型仍在执行，也不能把超时等同于操作未执行。
包里没有输入调用等待栈、ConPTY线程栈或完整原生远端事件接收记录，因此不能确认唯一现场根因。
约130 MiB transcript 是事实，但原有重开回放已经限为最近256 KiB，不能仅凭日志大小归因。
未在真实任务重放输入、重启游戏、补记验收或关闭业务问题。

## 已定位的代码机制与修复
1. 输入写入此前没有完成时限，前端 Promise 链会被一次永不返回的写入堵住。
   每个 PTY 现使用一个有界写入 worker；两秒未确认即锁定该输入通道。
   前端四秒 watchdog 同样停止后续队列，限制待发内容总量，不将 Promise 超时视为底层取消。
2. 输入绑定 inputSessionId。已经发出的旧 IPC 在终端被替换后会拒绝，不会误写到新连接；
   重建前丢弃未发送队列，新队列只绑定成功连接返回的标识。
3. 原生通知原来直接占用 RPC 接收线程做 DB/文件/工作流处理。
   现在即时轮次观察与有序通知落盘分离；投影队列限制256项/32 MiB，过载显式报错。
   无关输出增量不再进入 DB/工作流投影，socket 写入也有时限。
4. 当前是否忙碌只看最新原生轮次，历史残留 inProgress 不再挡住当前空闲会话。
   状态读取限时等待生命周期锁，重连不持有会话集合锁去回放日志。
5. 新增“重建终端连接”。服务端验证任务归属、最新原生空闲状态和后台操作已返回后，
   停止拥有的旧终端/执行器并重新接回原生会话。保留身份与历史，不提交模型输入或自动继续。
   活跃或未知状态被拒绝，需先使用已有中断/暂停流程；失败时仍保留明确的强制停止入口。
6. 自动推进等待已登记后台工具收尾，迟到结果完成后才能再次检查续接，避免与新一轮写操作重叠。

## 验证范围
- 故障注入：阻塞写入、有界返回、迟到成功后不重放、旧连接输入拒绝。
- 真实 loopback WebSocket：通知回调被阻塞时 RPC 仍及时返回。
- 原生服务夹具：历史运行状态残留、活跃会话拒绝重建、原生身份与记录保留、后台迟到工具。
- React：Unicode顺序、粘贴分块、超时停止、旧队列销毁、显式重建与输入身份绑定。
- 全量前后端检查及完整便携包校验随 terminal-freeze-fix-20261022 发布。
以上是可复现机制的回归验证；不冒充原始用户现场的完整线程栈复现。

## 使用
更新 APP 后，若模型已结束但终端无法输入，点击“重建终端连接”。
若提示执行或后台操作未结束，先核对原请求结果，再中断/暂停；不要重复提交原写操作。
如果问题再现，新的输入错误码、重建结果与原请求结果能进一步区分输入通道、原生状态和业务操作。
