## 本轮确认的问题

### 1. 快速回答时，继续操作错误地要求先暂停

用户已确认提交“多人”后点继续时看到过“仍在后台执行／请先暂停 AI”提示。
答案提交时间比首轮结束早约 73 秒，符合该分支的触发条件。

当前续接实现只处理了“已存在回执且那次执行仍在运行”的防重分支。首次继续没有回执时会调用 ensure_idle；如果发布问题的原轮次尚未结束，就要求先暂停。这把正常答题衔接变成了中断操作。
这也是最新版仍存在的边界问题，不能仅通过切换包解决。此前六题测试的回答耗时较长，没有覆盖“一题很快回答、原轮次仍在运行”的情况。

修复优先级：最高。提交后应保存并排队，显示“答案已保存，当前回复结束后继续”；当前轮次结束后核对最新版答案和阶段再接续。连续点击合并，主动暂停必须停止自动推进，不得盲目重放写入。

### 2. 正在运行的是旧 APP，任务流程版本不能证明程序已更新

正式窗口 PID 11388，16:54:30 启动，路径为 `Publish-Staging-Recovery/ABYA Desktop Development Tool.exe`。
该包构建于 14:17，早于续接修复包和 16:44 的 UI 包。任务显示的工作流 1.2.0 与 APP 修复版本是两回事。
另一个 Continuation 进程是此前隔离测试留下的进程，不据此认定它与正式任务共用数据库。

发布入口需要统一，并在界面明确显示构建日期和发布标识。多个同名程序都显示 v0.1.0，容易让用户误以为正在用最新版。

### 3. “连接恢复”和“任务继续”被同一名称混淆

终端栏的继续按钮只重开或连接终端，不自动发起模型工作；问答弹窗的继续按钮则发起需求处理。两处都称“继续原会话”，但行为不同。
应以明确的“继续任务”入口串联连接与执行，并在已运行时显示正在处理，而不是鼓励用户反复输入“继续”。

### 4. 已退出仍显示等待或运行画面

终端保留上次输出本身正常，但没有明显说明那是历史。步骤栏只要没有结构化计划，就显示“等待 Codex 列出本轮计划”，没有优先判断已中断状态。
截图同时出现“已中断”“Codex 已退出”“等待计划”“Working”，来自不同层次和时点。需要统一为当前连接状态、当前执行状态和等待谁操作；已暂停时不再用等待计划占位。
