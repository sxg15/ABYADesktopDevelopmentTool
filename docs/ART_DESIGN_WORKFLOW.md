# 游戏美术设计流程 2.2

新任务自动使用 2.2；已有任务继续原策略，暂停终端后从“升级流程版本”显式升级。升级保留文档、决定、证据和 Skill 备份，重新审查美术及受影响的后续阶段。

## 策划使用

在美术方案协作区打开“要求与参考”，查看原话、AI 解读、设计位置和实机对照。可补充要求、明确修订或撤回既有要求；撤回需要原因并保留历史。
保存补充要求后，可以让原任务 AI 核对最新记录。未保存的终端表达由 AI 通过带定位信息的摘录登记，界面标明其为 AI 摘录；策划可以对照原会话核查。
参考图可继续批量上传或粘贴。AI 应逐图查看、明确用途和取舍；来源图不会被计为设计成果。
策划继续通过原有四个节点确认需求、美术方案、执行计划与交付；没有新增固定轮次。

## 设计与验收

先从玩法、玩家行为、设备、输入、镜头和注意力推导设计，再确定风格。已有明确风格作为约束，不能被模型习惯覆盖。
完整新设计/整体重设计先记录5个领域原型、比较3个结构明显不同的低保真方向、留下5个产品专属决定，并做灰度、换 Logo、换平台、通用性及容器移除检查。局部修复与已确认方案实施按范围执行。
运行后补充默认风格、产品识别和连续交互审查。方法和淘汰理由保存在确认单及现有设计记录里；后台不以条目数量或自评分数宣布美术合格。
每条有效要求应关联当前正式方案的位置；新输入、新图或设计变化需要复核。文档提交检查只验证材料和版本，实际画面仍需审阅。
先做代表核心循环的场景与关键状态，拆分角色、场景、道具、UI、动画和特效规格，再按能力选择制作方式。
定稿前核查能力；实现阶段逐条关联当前游戏版本、对象、图像/视频证据、对比与残余差异，不能以日志或编译成功冒充视觉验收。

## 积累与参考案例

在“美术设计库”中让 AI 整理案例草稿，查看具体成果、上下文、视觉规则、制作方法、适用条件与限制。
明确填写满意的部分，再点“满意并收录此案例”。这不会批准整个任务，也不自动把概念图标记为实机验证。
库保留独立媒体快照，因此任务删除后已收录案例仍可查看。案例修订生成新版本；停止推荐保留历史与既有任务快照。
“让 AI 评估并参考”请求原任务读取固定案例，解释借鉴、适配及不采用部分，查看任务内媒体，再结合本次要求设计。
导出 ZIP 仅包含整理后的文本和素材；导入检查格式、路径、大小与哈希，标明外部来源，不冒充本机策划认可。
案例检索与使用不训练模型权重，不将过去验收当作当前游戏验收。系统不会预先创建虚构的满意案例。

## 维护与验证

SQLite 是任务与案例元数据来源；workflow.json 和 HTML 是导出。不要直接修改导出来推进状态。
通用 Skill 与游戏专项 Skill 的参考全部使用相对路径；仓库 .codex 为规范来源，sync:workflow 同步 .grok，运行包复制完整资源。
自动回归覆盖遗漏、原话保护、来源变更、版本过期、媒体校验、案例独立性、导入导出及人工操作边界。
scripts/art-design-preview.html 为真实 React 组件的隔离交互预览；其图片和案例不是已完成游戏或策划认可证据。
