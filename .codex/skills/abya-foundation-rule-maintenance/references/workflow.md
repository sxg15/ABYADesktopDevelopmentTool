# 状态与维护流程

## 持久数据

`state/ledger.json`按真实document_id去重，Wiki URL与docx URL作为同一文档的别名。`rules`保存不可含糊的用户规则和版本；`documents`保存来源、基线、旧稿/新稿身份；`applications`以规则ID＋规则版本＋文档ID唯一关联；`history`保存状态变化；`cloud`保存唯一飞书台账地址和最近核验版本。

专用飞书台账是可读查询入口，不是授权信号。刷新前读取当前版本，保留用户备注；发现云端人工调整规则或状态时先核对证据、合并到本地，不能无条件整篇覆盖。已知文档目录来自维护表有链接记录、已交付记录及相关云文档搜索；新增文档或发现漏项时补登记，查询应明确目录覆盖范围。

## 状态

| 状态 | 含义 |
|---|---|
| pending | 已排队，尚未执行该版本迁移 |
| needs_review | 可能已符合或需要核对，不能当作已应用 |
| in_progress | 正在执行已授权范围 |
| partial | 本地/正文/配图/输入包只完成部分，列未完成项 |
| applied | 对应版本已在文档及必要交接包落实，且回读核验有记录 |
| blocked | 有具体权限/材料等阻碍，记录原因与恢复条件 |
| not_applicable | 不属于该规则适用范围，必须给理由 |

迁移进度与体验验证分开。`applied`证明设计文档已落实；`runtime_validation=not_tested`仍表示未做真人或运行验证。不能凭标题、关键词、Skill更新或一个成功响应标已应用。

已应用证据至少有文档URL、远端revision、核验日期、关键正文摘要、交接包检查结论和验证层级；输入包不存在时明确写“不适用”及原因，不默认为已通过。新稿不能用“待批量维护”绕过生效规则。

## 指令语义

- “新增底层规则/先记着”：新增或升级规则，更新适用旧稿记录与专用台账，不执行迁移。
- “X文档有什么待维护/规则Y还有哪些没改”：只读查询，可刷新文档清单；不能顺手改正文。
- “把规则Y应用到X/执行这批维护”：执行指定交集；无重复确认要求。逐份读取、修改、回读、校验后记账。
- “新设计一个玩法”：读取全部生效规则直接设计；交付时逐规则记录证据，不等待旧稿迁移。

## 脚本

`rules`读取生效规则；`query --document <名称/URL/ID>`或`--rule <ID>`查询矩阵；`register-document --input file.json`登记文档并为适用规则补记录；`upsert-rule --input file.json`登记新规则版本；`set-status --document <ID> --rule <ID> --status <状态> --evidence file.json`更新记录；`render --output draft.xml`生成专用台账内容；`validate`校验引用与证据。

脚本对持久更新加短文件锁并原子替换，网络操作在锁外完成；冲突时重新读取合并，不能删除别人的锁或强写。不得将迁移按钮/原始CLI命令塞进游戏界面。
