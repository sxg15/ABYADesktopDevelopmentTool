# 外部编辑、导入和存档发布

## 给外部工具的编辑契约

为具体项目写一份实际路径与格式说明，不能只说“修改关卡表”。至少包含：

- 唯一数据源的绝对路径及工作区相对路径，CSV/JSON/其他格式，编码、换行、引号与转义规则。
- 字段名、类型、必填项、唯一 ID、启用/禁用语义、版本、排序规则；提供一个有效例子。
- 内容约束、共享规则验证方式；关卡若包含地图，明确坐标、边界、起终点、合法符号及尺寸。
- 可编辑字段与派生字段。评分、答案、哈希等派生值重新计算，不能信任外部填入值。
- 实际校验/构建命令、错误报告位置、失败时旧版本是否继续可用、游戏内读取方式。

`id,enabled,seed,map,notes` 只是网格游戏可选示例；答题、跑酷和反应游戏需要各自的数据模型。不要在通用流程中固定 CSV 结构。

## 导入顺序

1. 读取最新源文件并记录哈希、启用数、禁用数和分类数量；留存可回退的输入与目标绑定备份。用户明确取消的旧内容限制不要偷偷恢复。
2. 执行格式和规则校验。校验器和实际游戏共用规则函数或等价性测试，不能用不同终止判定验证内容。定位错误到行、ID、原因；未经验证的内容不发布。
3. 输出游戏内容包、验证报告和版本信息。若采用运行时生成，设置有限尝试与已验证备用内容；备用必须满足当前约束，不能暗中降低标准。没有合格备用时明确失败。
4. 比较生成内容与存档绑定，仅修改相关目标；只改题库时不要批量覆盖 UI 和其他脚本。按平台要求验证精确脚本目标及架构，使用最新 revision 写入。
5. 用原生编辑器工具绑定、保存、再读回。比较内容/脚本或其哈希与构建产物一致；确认脏状态和目标存档路径。
6. 新建或重启加载该存档的 Host/Client，检查内容版本、池数量和实际抽样。相同种子与题号输出一致。已有实例可能保留旧内存题库，不能把保存成功当作热更新成功。

不直接覆写未掌握格式的原生 PBUI/PBLevel 等序列化文件：事件值可能是嵌套 JSON 字符串，原始 Lua 不能替代外层动作容器。优先使用公开原生接口；缺少能力时记录阻塞，不能用未经往返校验的文件替换冒充已导入。

调用超时后，先检查进程、保存状态及目标内容，判断操作是否已经执行。不要盲目重复修改；重试次数有限，保留错误报告并说明实际停在哪一层。

## 发布记录

记录源文件哈希、内容版本、规则/评分版本（如适用）、构建命令、有效内容数、原生目标、保存读回结果、测试实例及运行确认。仅统计真正执行的测试，不把“可求解”写成“全部真人玩过”。

源码改完、构建成功、绑定完成、保存成功、运行实例更新是五种不同状态；交付时明确已经到达哪一种。
