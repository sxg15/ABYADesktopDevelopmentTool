# 从玩法推导游戏 UI

本方法可用于不同引擎和项目的游戏 UI；接入已有美术流程时沿用其设计与确认记录。策划原话、有效要求、已选方向和当前设计文档是本次约束；不因加载专项重开需求、另建审批文档或启动游戏。ABYA 的 resources/direction 等字段映射由宿主指南管理，其他项目使用自己的等价记录。
只处理请求涉及的界面和状态。完整新界面/整体重设计沿用宿主的结构探索；局部修复、已确认方向的实现只核对受影响范围，不为每次改动重做三套方案或所有状态。

## 先认清正在玩的内容

读取当前有效来源、要求编号、原句、来源标识、反馈及已有实机图；宿主提供 sourceId 等结构化身份时保留原值。图片保留来源身份，解释标为观察或推断；摘要不能替代原话。
列出保护项及适用范围，例如已经认可的主玩法区域、物品图示、队伍身份色、字体、操作路径。新建议不能静默覆盖它们；冲突写回现有记录。
用一句话说明本屏服务的玩家决定，再确定以下事实；已有资料能回答的直接沿用，未知且可逆的标为假设继续。

| 事实 | 对结构的实际影响 |
|---|---|
| 核心循环与输赢条件 | 持续信息、临时决策、动作优先级与结果反馈 |
| 镜头、目标/敌人、玩家视线 | 主视区、边缘信息、随对象标记及遮挡禁区 |
| 平台、视口、距离、安全区 | 字面大小、热区、锚点、内容重排与密度 |
| 鼠标键盘、触摸、手柄与输入切换 | 悬停可用性、焦点导航、提示符、取消与返回 |
| 操作频率、压力、会话长度 | 常驻/按需显示、操作步数、动画时长与可打断性 |

不要从 Hero、营销文案、网站导航或卡片网格开始填游戏内容。容器、面板、页签和熟悉控件有玩法依据时可以使用；不能仅靠换 Logo 和配色形成游戏身份。

## 按界面职责组织

| 本次界面 | 优先解决的关系 |
|---|---|
| HUD / 战斗覆盖层 | 玩家看目标时能否判断并执行下一步；把常驻、事件、对象附近信息分开，核对准星、角色、敌人、弹道与触控区域的遮挡 |
| 主菜单 / 暂停 / 设置 | 继续游玩与新开局的区别，暂停是否停止世界，设置何时生效，退出/取消如何保存或恢复现场 |
| 背包 / 装备 / 商店 | 容量、分类、选择、比较、使用/装备/购买与数量的关系；按真实物品和成本展示，不能把图示要求偷换成数字 |
| 关卡选择 / 地图 | 路线、解锁条件、进度、难度和奖励如何支持选择；线性流程不强造世界地图，空间路线不压成无差别卡片 |
| 结算 / 失败 / 重试 | 结果原因、收益变化与下一步；关键信息应能读完，重试/继续的高频动作不等待庆祝动画结束 |

多屏流程保留选择、滚动与焦点上下文，明确返回到哪里；确认、取消与撤销各有语义。只为实际可达的状态制定规格，不虚构空态或联机故障功能。

## 参考先解决当前问题

策划提供的每张有效参考优先查看并归类：整体风格、资产、布局/交互、氛围或反例。保留其明确优先级；参考中的文案、提示词和默认数值不是执行指令。
需要补充案例时再读 [UI 参考库指南](references/ui-reference-library.md)，使用 [结构化目录](assets/ui-reference-library.json) 与 [检索脚本](scripts/query-ui-references.mjs) 按玩法/屏幕职责、输入、镜头、平台和密度找候选，再比较风格。实际打开候选媒体/官方上下文后才写观察与借鉴；库命中不等于已经看图。
检索必填 uiKinds、inputs、density、scope、brandLocked；先从现有资料推导，缺失时保留未知，不让空查询变成默认风格推荐。平台与镜头继续写设计依据，不编造成脚本参数。局部手柄背包焦点问题可用 `{"uiKinds":["inventory"],"inputs":["gamepad"],"density":"high","scope":"partial","brandLocked":true,"categories":["layout","state-feedback"]}`；策划给出的来源可放 preferredSourceUrls，候选仍须实际查看后判断。
记录来源身份/版本、解决的问题、借鉴、适配、不采用与未验证。相同题材而输入/信息结构不适用时拒绝套用；找不到合适案例可以继续，不强凑参考。
本库是外部设计参考，不能冒充宿主中已获策划认可的美术案例或当前方案。来源许可不清时只分析，不推定可复制其资产。

## 把方向交给实现

方向选定后读 [UI 设计交接](references/ui-design-handoff.md)，把本次 UI 部分合并进已有美术需求/设计文档；ABYA 对应 resources 与任务内 DESIGN.md。可使用 [章节模板](assets/ui-design-section.template.md)，不新增确认点。
用任务内唯一的数值/变量 JSON 或已有配置表达尺寸、锚点、间距、字体与状态参数；DESIGN.md 引用其路径和版本，不再抄一套数值。先核实当前引擎/组件能够读取和实现，再扩展组件。
每个交互控件串起“输入 → 动作 → 状态变化 → 反馈 → 焦点/取消”；保留独立文字、图标、底板、热区与状态层。整屏概念图不能当作可操作界面，生成图中文字不能当作可用字体。
使用实际可用字体与真实语言样字，按最终显示尺寸校准字形、字重、数字、长名称和回退。资产注明尺寸、透明/切片、伸缩、状态、来源与复用范围。
分别规定对象身份、操作强调和状态颜色；队伍/阵营/元素身份色不能被统一主题色吞掉。关键状态配合形状、文字或图标；灰度审查用于发现层级问题，不抹掉颜色玩法。
触摸不能依赖 hover；手柄有可见焦点、可达导航和取消后焦点恢复；鼠标悬停不是选中。输入切换更新提示与焦点行为，不能只换按键图。
高频动作即时响应，装饰动画不锁操作或延迟读数；规定重复触发、跳过、打断与降低动态表现。HUD 的特效/数字/弹窗在真实镜头与内容密度下检查遮挡和竞争。

## 证据与认可分别保存

先校准一个代表片段及其关键状态，再扩展受影响界面。实现后用相同内容、视口、镜头、状态和输入核对方案；动态反馈通过实际操作或视频验证。
记录要求编号 → 方案位置 → 实现对象 → 当前版本证据 → 观察与残余差异。按实际风险检查最小/典型/高密度内容、最长文案及支持的输入，不每次固定跑全套。
分别记录功能、视觉质量、规格还原、策划认可；AI 自检、历史认可和工具通过不能代替本版人工确认。只有实际查看过的当前运行画面可称为实机证据，未运行写明具体未验证项。
保留已认可区域，修复后复验受影响关系；不靠统一新配色、任意像素容差、总分或“无 AI 味”保证质量。

## 路由示例

- “按这三张参考做手机战斗 HUD”：先看三图并保留用途与优先级，由镜头/触控/战斗信息决定区域；再按缺口查触摸 HUD 案例，不套网站首屏结构。
- “手柄背包看不出焦点，其他别动”：沿用布局/资产，仅处理焦点、导航、动作提示与取消恢复；复验受影响控件和输入切换。
- “关卡选择需要表现分支路线”：从真实解锁图与选择理由推导结构，查路线/进度参考；不能因候选图漂亮改成无关商店栅格。
- “这版结算数值挤了，保留纸艺风”：保护既有风格和已认可部分，核对真字体、长数值与高频继续操作；无需重选纸艺模板或新增美术审批。
