# MCP 场景验证与 Player 基线

通过已配置的 abya MCP 服务执行游戏验证，不运行旧 runtime-scenario 或 player-baseline CLI 脚本。
场景文件是保存在任务内的声明式验证计划，记录当前版本、构建、存档、目标实例、步骤、真实参数、
观察与预期结果。可用提供方的工具编排能力顺序调用 MCP；没有该能力时逐项调用相同 MCP 工具。
不通过 Shell 包装 ABYA 业务操作。普通文件格式/数据检查可使用提供方的代码编辑与执行能力。

## 可复用场景

| 场景 | 观察 |
|---|---|
| 单人闭环 | 准备、开始、真实输入、结束、返回的真实状态与画面 |
| 双端同步 | 同一房间/轮次、不同真实实例的身份和结果一致性 |
| 输入边界 | 阈值两侧、卡外起手、释放、取消、真实失焦、跨状态输入 |
| 固定序列 | 明确标注独立夹具，不替代正式候选自然输入 |
| 机器人 | 正常观察和动作通道、实际接受及计分、本游戏批准容量 |
| 保存重载 | 实际保存后从另一个托管实例冷加载同一完整版本 |

步骤使用 game_runtime_call_tool，toolName/arguments 来自当前 PB MCP schema。
静态检查、工具响应、断言、真实功能以及用户验收分别记录；isError=false 不等于玩法通过。
原始结果通过 development_production_update 登记为真实证据和自测；不要编造返回数据。
同一检查无新结果不重复执行。只读查询可有限重试，写入未知时先用
 game_runtime_operation_receipt 和实际目标读回对账；相同操作不得盲目重放。
取消请求不是回滚；只有实际终止与结果确认后才继续依赖该操作的写入。

初始化异常先保留完整启动报告与原日志，再按首次异常、次数与有效堆栈检查。
缺少观察接口不直接证明 PB 缺陷，换有效验证方式时仍需覆盖同一批准要求。

## 构建基线

使用 development_production_runtime_baseline 读取实际所选构建的摘要；query 可以按关键词检索。
缺少基线不是游戏失败，也不要求每款游戏重新审计全部平台。
在真实托管实例上完成基础测试后，可通过 game_runtime_qualify_player 提供 instanceId 和 testIds。
APP 直接向 PB MCP 读取报告并核对完整构建指纹，不接受模型填造的通过结论。
基线仅证明实际报告覆盖范围，工具目录存在不表示该能力全部验证通过。
当前游戏的输入、规则、视觉及保存验收仍需对应真实版本和批准需求。
