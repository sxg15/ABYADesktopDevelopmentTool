# 从产品推导界面

你承担的是完整的产品设计、交互设计、视觉设计与前端实现任务。这里的前端不限于网页：目标可以是移动或桌面 App、专业工具、编辑器、游戏界面、电视或触摸终端。当前任务的实际范围决定交付，不因为这段原则扩展用户需求。
不要以生成一个“看起来不错”的通用 UI 为目标。根据领域、用户、任务、内容、平台、输入方式、使用频率和真实环境，推导出适合这个产品的界面。
用户应当感觉“这个界面之所以这样设计，是因为这个产品本身就应该这样工作”，而非熟悉的模型模板只换了文字、颜色与 Logo。

必须按以下顺序建立设计依据：
产品是什么 → 谁在使用 → 最重要的任务 → 设备与环境 → 输入方式 → 使用频率与时长 → 领域的信息组织与工作流程 → 用空间、时间、层级、颜色或交互表达的关系 → 界面形式。
禁止从模型最熟悉的视觉组合、SaaS/Dashboard/Admin/组件库 Demo、流行展示稿或对 Apple/Linear/Notion/Stripe 的模仿开始设计。先读用户提供的品牌与风格要求，把它们作为约束；用产品任务决定如何应用，而非自行否定用户选择。
先回答用户打开后第一件事、最常做的三件事、持续可见的信息、最快完成的操作、高频操作与低频高风险操作，以及扫描/阅读/比较/创作/控制/监控的差异，最后才讨论视觉风格如何成立。

目标是让用户感到“这个产品就应该这样工作”。减少模板感依靠任务结构、内容、交互与视觉细节之间的因果关系；不以装饰数量、设计术语或“像真人做的”作为验收依据。
本 Skill 不绑定项目、模型、框架、组件库或品牌；内部引用均为相对路径。项目的实现、发布、数据和人工确认契约继续适用。

## 使用范围

- 新产品或整体重设计：完成下面的设计推导、代表场景实现和验收。
- 已有产品：先读代码、设计资产、现有规范和实际界面，辨别可复用部分，再处理有证据的问题。
- 局部视觉或交互修复：只分析受影响任务、组件及状态，不重新发起整套需求收集。
- 优化 AI 制作流程：读 [流程接入](references/workflow-integration.md)，将设计判断放进已有节点。
- 用户已有明确品牌、风格、参考或方案：沿用其选择，补足工作逻辑；不因个人审美推翻。

## 1. 先确定产品事实

先回答：产品服务谁，用户打开后做什么，最常见的三个任务是什么，哪些错误代价最高。
再确定设备、视距、鼠标/键盘/触摸/手写笔/遥控器等输入、会话时长、使用频率、协作和环境限制。
识别核心领域对象、状态、关系、真实工作顺序，以及用户主要在扫描、阅读、比较、创作、控制还是监控。
从现有材料取得证据，区分已知事实、设计推断、待验证假设。影响主任务的缺失信息才向用户提问，其他项采用明确的可逆假设继续。
形成精简的设计依据；需要组织资料时读 [设计记录](references/design-record.md)，不机械填写无关字段。

## 2. 从任务推导信息与交互

按“触发 → 用户动作 → 系统反馈 → 下一步或恢复”走通主任务，确定持续可见的信息、最快操作、低频配置和高风险操作。
用真实对象及关系决定空间：时间顺序、对象层级、并列比较、地理位置、连续画布或工作步骤应有对应表达。
完成内容优先级与低保真结构后，才选择导航、列表、表格、画布、面板、卡片和标签页。选择要能解释其对任务的帮助。
不要先选 Sidebar、Hero、Bento、Dashboard 等版式再填内容；这些形式并非禁用，有任务依据就可以采用。
规定选择、编辑、提交、撤销、取消、异常恢复与焦点去向。跨屏流程明确数据与选择如何保留。
新方向确有结构分歧时，在同一真实任务和内容下比较候选方案；不能只换颜色当作不同设计。已有清晰方向时不强制多方案。

## 3. 建立有依据的视觉语言

先查看可访问的现有产品画面、品牌资源和用户参考；需要外部参考时实际打开并查看，记录来源与适用原因。
参考应解决具体问题，例如长列表扫描、时间轴缩放或远距离状态辨认；提炼原则而非复制某品牌整套外观。
不能把未查看的链接描述为已分析的参考，也不能把无法取得的素材假定为可用。
在结构明确后确定视觉主张：哪些内容最先被看见，什么负责分组，产品的辨识度来自什么。
将主张落实为可复用规则：字体与数字、尺寸层级、网格与密度、间距、语义色、边界与层级、图标与图像、反馈动效。
每个显著选择都应有产品、品牌或感知上的目的。表达性、趣味和装饰可以成立，但必须适合使用场景。
避免无依据地组合大圆角、悬浮卡片、柔光渐变、磨砂、胶囊标签、均匀栅格和大片留白；换成黑白、锐角或高密度也不是自动改进。
字体需适合实际语言、字重和平台；验证中文、英文、数字及回退表现。不要用一款“高级字体”代替排版设计。
颜色区分动作、选择、状态和对象身份，不让同一种强调承担所有含义；关键状态同时有文字或形状表达。
装饰、阴影、图标和动效共享一套逻辑。静态界面层级应先成立，再增加反馈动效。

## 4. 用真实内容形成代表场景

先做覆盖主任务和核心视觉规则的一段完整流程，再扩展其余页面；营销封面不能代表工作区质量。
使用可信的领域内容、数据量、长名称、中文、多位数值及真实状态比例；模拟内容需标明，不能伪装成业务成功。
检查默认、选中、焦点、禁用、加载、空、失败、部分成功等实际可达状态；不为不适用状态造功能。
需要美术资产时先列复用/新增范围、用途、目标尺寸、缩放或切片方式、透明区域、状态和替代方案。
整屏生成图只能作为概念参考，不能替代可交互布局。文字、控制和动态数据保留独立可实现结构。
栅格生成适合角色、材质、插画等资产；已有矢量、图标体系和代码原生图形优先沿用适合的制作方式。
资产应统一视角、光照、线条、色彩与细节尺度；在最终显示尺寸验收，拒绝占位符假冒正式素材。

## 5. 在目标平台实现

复用已有架构与组件，提取设计变量和公共状态，避免逐页堆叠特例及相互覆盖的样式补丁。
平台规则按 [平台与输入](references/platform-and-input.md) 选择适用项；WebView 并不意味着桌面工具应采用网页落地页结构。
明确窗口/视口边界、滚动区域、内容溢出、缩放及输入反馈；跨设备时按任务重新组织，不能只同比缩小。
实现不支持原方案时，修订设计并记录取舍，不默默以占位控件或默认组件替换关键体验。
局部美术变更保留业务语义、已有内容和用户工作状态。未经请求不扩大到整套产品重构。

## 6. 以运行结果迭代

实际运行目标界面，观察截图并操作主任务；仅有编译成功、DOM 检查或概念图不足以确认设计完成。
按 [视觉与交互验收](references/review.md) 检查产品特异性、层级、排版、密度、资产一致性、平台行为及关键状态。
先修复任务阻断、信息误导和输入障碍，再处理层级、排版、对齐与细节；修复后复验受影响的场景。
比较必须使用相同任务、内容、视口和状态；不要通过缩小截图、隐藏长内容或更换数据美化结果。
自动检查负责可机器验证的边界，视觉判断仍需实际查看；不把自评总分当作客观质量或人工批准。
没有运行或截图能力时，交付可审阅方案及具体未验证项；如实说明限制，不宣称完成视觉验收。

## 交付原则

策划或用户的原话与来源、设计解读、方案位置和运行证据分别保留；摘要不能代替原话。新增要求不自动取消旧要求。修改方案前核对有效要求与未关闭反馈，不能默默降级、遗漏或用历史案例覆盖当前明确指示。
复用案例时先查看其图像、用户任务、平台、制作方法和适用边界，记录借鉴、适配与不采用的部分。历史认可只属于其明确范围和版本；不当作新任务验收，也不把案例入库称为模型权重训练。
交付实际改动、关键设计理由、查看入口和已执行的验证；记录仍存在的具体问题及影响。
完整设计应能追溯“产品事实 → 任务/内容 → 结构与交互 → 视觉规则 → 实现 → 证据”，无需为每个小改动另建六份文档。
尊重当前工作流的审批；不要自行新增固定轮次、重复确认点或把设计自检说成用户验收。
