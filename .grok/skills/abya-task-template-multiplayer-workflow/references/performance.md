# 性能原因分析与修复

## 先固定测量条件

记录构建/存档版本、硬件、窗口分辨率、图形设置、目标帧率、垂直同步、前后台/最小化状态、实例数量及网络拓扑。不要把单实例前台与双实例后台直接比较。托管后台窗口是否继续正常渲染须验证。

同一内容和对局阶段预热后，至少取得足够覆盖问题的连续样本。稳定场景可先用 600 帧作初步样本；间歇卡顿还需更长、重复窗口。记录平均帧时间、P50/P95/P99、最大值、超过预算的帧数与比例；FPS 由总帧数/总真实耗时计算。报告统计口径，不能把平均瞬时 FPS 当成平均帧时间倒数。

优先用引擎实际帧时间/Profiler；确认采样时钟。游戏 deltaTime 可能被 timeScale 或最大步长限制，不能无条件当成真实墙钟耗时。测量期间避免截图、密集 CLI 查询、大量日志及额外自动化渲染循环。确认每个视图只启动一次，旧脚本已经停止。

## 逐层隔离，只改变一个因素

在可还原的测试实例中比较：完整游戏 → 暂停本地动画 → 静态 UI → 分组启停 HUD、名单、核心玩法区或主场景重绘 → 如工具支持再区分网络、脚本、布局、渲染与资源加载。

| 证据 | 可以得出的结论 | 不能据此声称 |
|---|---|---|
| 完整视图慢，停视图后快 | 视图相关总工作量是主要调查方向 | 某一个 setter 或引擎 bug 已确定 |
| 单独重复设置一个属性仍流畅 | 此隔离负载下没有复现 | 属性在复杂层级里一定没有成本 |
| 多实例比单实例慢 | 可能存在共享 CPU/GPU/内存争用 | 网络代码必然有错 |
| 内存占用较高 | 需要看增长、回收和资源持有 | 已证明泄漏 |

引擎问题需要 Profiler 调用栈、最小复现、公开接口行为或可访问源码的证据。拿不到引擎内部证据时标注“疑似/尚未定位”，列出下一步需收集的数据。端口冲突、日志异常与掉帧相关性也需要独立验证。

## 优先修复可控实现成本

- 缓存 UI/对象代理及最后写入值，仅在属性变化时调用 setter；避免每帧全量枚举节点。
- 内容或布局尺寸变化时重建静态玩法区；普通状态变化仅更新受影响元素，避免反复重设整个场景和资源。
- 连续动画按实际帧更新；整数时间、比分和名单按状态变化更新。可从 HUD 10 Hz、装饰 15–30 Hz 等起点实验，但频率由体验与测量确定，不作为硬性标准。
- 核对原生属性的真实含义。文字字号与节点尺寸可能是不同接口，不能凭同名属性猜测类型。
- 减少热路径对象分配、字符串拼接、日志及重复反序列化；缓存内容解析与可复用计算。分析实际开销后再决定优化范围。
- 使用差量同步，不在每次输入后重复发送不变题库或全场状态。输入序号与版本校验仍保留。
- 服务端使用正确的权威截止判定；即使显示/广播节流，也必须在操作判定时检查截止，不能延长比赛或重复计分。
- 定时器有明确初始化与清理，避免重复订阅、循环叠加和不可达分支，例如 tick 已自增后仍依靠 tick==0 完成初始化。

## 复测与交付

先跑规则与联机回归，再以同一条件测量优化后的完整 UI。检查加入、准备、持续操作、推进、截止结算和重开；视图关闭后的数据只能作为隔离证据。

报告使用以下格式：

| 版本/实验 | 场景和实例数 | 平均 ms | P95/P99 ms | 超预算帧比例 | 样本数/时长 |
|---|---|---|---|---|---|
| 修改前完整游戏 | 实际条件 | 实测 | 实测 | 实测 | 实测 |
| 隔离实验 | 唯一变化 | 实测 | 实测 | 实测 | 实测 |
| 修改后完整游戏 | 与基线一致 | 实测 | 实测 | 实测 | 实测 |

逐项区分“已证实原因”“已修复且复测有效”“疑似引擎成本”“未执行检查”。无法完成完整运行复测时明确说修复尚未获得性能验证，不宣称已经流畅。
