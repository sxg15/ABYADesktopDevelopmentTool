# 视觉细化与实机审查 · 1.0

在产品任务、结构与风格已经明确后使用；局部修复只读取受影响部分。
本模块补强层级、排版、间距、颜色、层次与反馈，不另开需求收集或审批。
当前明确要求、项目规范与已确认方向是设计依据；通用经验不能覆盖它们。
遇到可读性、能力或规范冲突，指出影响与可实现的处理，不静默删改要求。

## 三个使用时机

1. 设计前：从有效要求和已查看的参考形成简短视觉约束，写入原设计记录。
   说明首先看什么、持续看什么、动作/选择/状态/身份各用什么表达、密度依据、
   字体与图像尺度、必要反馈、既定风格与不能改变的体验。不默认选配色或组件。
2. 方案提交前：逐条核对要求与禁止项；检查真实内容下的层级和风格一致性；
   对核心效果确认制作能力。概念图、参考图、实现画面分开标注。
3. 实现后：查看实际画面并操作代表任务，对照同内容、视口、镜头、状态的方案。
   修正有证据的问题并复验受影响范围；图像存在、代码通过和 AI 自评都不是验收。

## 按问题读取

- 重点不清、配色割裂、间距混乱、组件机械重复：读 [规则与适用条件](visual-refinement/rules.md)。
- 桌面多面板、中文、游戏 HUD 或不同输入：读 [平台与游戏适配](visual-refinement/platforms.md)。
- 评审、修复和确认改动收益：读 [审查与对比](visual-refinement/review.md)。
- 需要机器验证明确色对或导出已定义变量：读 [工具边界](visual-refinement/tools.md)。
- 追溯改写来源：读 [来源与适配说明](visual-refinement/attribution.md)。

先判断失败场景，再决定是否使用某条建议。没有问题证据时，不为满足清单改掉
刻意选择的高密度、硬阴影、像素字、身份色或必要边框。
规则编号只帮助追溯；策划要求、平台规范、实际操作证据也能独立构成判断依据。
角色、场景、材质和特效创作继续由游戏美术方法负责，不强行套用 UI 排版清单。

## 经验积累

在案例原有字段中保存：问题、采用方法及原因、必要例外、制作与实机差异、
修正结果、认可范围和适用限制。只有明确满意才整理收录，不因审查无问题自动入库。
使用案例前实际看图和上下文，再记录借鉴/适配/不采用；库为空也能继续设计。
新任务必须重新验证；历史认可不是当前验收，也不是模型权重训练。
