# 在现有七阶段中使用

| 阶段 | 选用方法 | 落在现有材料中的内容 | 验证方式 |
|---|---|---|---|
| 需求整理 | init / shape / clarify | 用户、玩法、设备、输入、任务、成功条件；复用已确认答案 | 对照原始需求，标明未知事实 |
| 资源美术 | layout / typeset / colorize / distill / quieter | 代表画面、注意力层级、参考取舍、视觉规则、字体样字 | 真实内容与状态下的渲染，不仅是概念封面 |
| 方案预检 | adapt / harden / animate | 平台可实现性、布局模式、资源规格、交互状态与异常恢复 | 对关键不确定能力做小样；不能把文档存在当能力通过 |
| Lua 实现 | extract / document / optimize | 共用参数、组件、资产绑定、实机标定 | 对字体、间距、热区和性能分别验证；不声称 CSS 数值等同引擎像素 |
| 试玩与修改 | critique / audit / polish | 具体缺陷、影响、修复证据与保留理由 | 同版本同镜头同内容；鼠标、键盘或触控实际操作 |
| 交付验收 | harden / polish | 可交付范围、已知限制、当前版本证据 | 功能、视觉、规格还原与人工验收独立记录 |
| 收尾复盘 | document / extract | 可复用方法与适用边界 | 仅明确认可范围进入满意案例，保留来源与版本 |

## 防止技能整合增加用户负担

这些检查在后台或专业视图进行。策划默认只看本轮结果、变化与需要决定的事情。
多个检查发现同一问题时合并问题实体，保留各自证据，不复制成多个待办。
没有实际问题时不生成空检查面板，不强制策划逐项签署 46 条规则。
不把“去 AI 味”当作可测质量指标；使用阅读困难、定位耗时、误触、遮挡、错误恢复和具体还原差异。

## 平台转换例子

- 文字溢出：Web 测 DOM 与滚动边界；Unity 测 RectTransform、文本换行与实际渲染截图。
- 对比度：UI 颜色对可测；动态场景下还需代表背景/光照与状态截图，不能只用静态 token 计算。
- 布局动画：Web 避免频繁布局抖动；Unity 核对 Canvas 重建、布局组件和实际帧耗，不能直接移植 CSS 检测结论。
- 图片失效：Web 检查 src；Unity 核对 Addressables、Sprite/Texture 绑定、加载失败与替代状态。
- 玩家识别：玩家色必须同时有名称、位置或图形区分；不可为了精简配色删除阵营信息。
- 手机 / 手柄：按热区、焦点、返回、手部遮挡与实际设备设计；缩小桌面图不算适配。

## 本次设计的适用例外

单字体适合中文操作工具；阶段编号表达真实顺序；棋盘格并非装饰卡片墙；游戏画面有自己的色盘；原型状态有显著模拟标识。
不将营销页专属规则强推到长时间工作台，不将桌面工作台的克制强推到需要情绪和反馈的游戏画面。

## 发布整合清单

要进入正式 ABYA 分发时，以项目 canonical 技能树为源，同步 module Skill、版本契约与 CHANGELOG。
仅分发所需设计参考；浏览器 live/生成工具或 detector 可执行文件是否随包分发需单独验证体积、运行时与许可。
新任务按新版本使用；旧任务不自动换 Skill，显式升级须保留备份、历史与仍有效的批准。
本地适配 Skill 独立于现有个人技能同步脚本，不会被旧的三目录同步静默覆盖，也不冒充已更新的 APP 包。
