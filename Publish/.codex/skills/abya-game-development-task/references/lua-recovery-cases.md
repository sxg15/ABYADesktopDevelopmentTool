# Lua 实现中的误判案例

下列案例来自项目反馈。版本、目标对象、字段值和权限均以手头任务回读为准。

## 多数颜色 B：components 被拒绝

表现：三档供题的离线检查已通过，架构验证器拒绝了清单。任务起初请策划找维护方补字段说明；后来使用现有接口修正字段，验证错误与警告归零，Manual 设置保存、独立冷加载通过。

复查路径：

1. 在当前任务的指定 Player 上发现并描述 `editor_gameplay_architecture_validate`。展开输入 schema 的 `properties.manifest.properties.components.items`，读取必填项、类型和枚举。只看顶层 `manifest` 的摘要会漏掉这些信息。
2. 对照诊断的字段路径、实际输入及返回的 `allowedValues`。例如 `scope` 表示职责，`target.kind` 表示对象类型。用当前存档的 `editor_gameplay_architecture_snapshot` 查实际目标、事件和可用的绑定示例；不能从对象名字猜枚举或事件 ID。
3. 仅修正出错的字段，用同一目标重新校验完整清单。通过后在本轮直接绑定对应 Lua、保存、冷加载并验证界面或计分。供题离线通过只能说明供题已验证。

## 连线加法 C：旧预检卡写着“原始新建问题”

表现：错误回执为 `runtime_not_ready / not_executed / initializing`，后续已有档保存和冷加载通过。最初要求策划再授权新建路线；复核原始运行记录后，确认它走的就是已有档路线。Host 和独立 Client 后来均能进入玩法，Lua 初始化通过。

复查路径：

1. 回读当前阶段、构建指纹、存档和关卡身份、预检运行编号、实际路线、检查项和清理状态。同一问题 ID 的旧标题可能没有随路线更新。若只读探针明确返回“初始化中且未执行”，等待就绪，再读一次。写入结果未知时先查回执和存档，避免重复创建或保存。
2. 对当前动作判定证据范围。已有档修改需要当前同范围的加载、保存、冷加载证据；新建任务还需实际的新建证据。Host/Client 就绪说明启动链已通，交出可试玩包仍需实际操作并核对结果。
3. 用当前版本的回执更正问题归因；按正式接口解决已验证的问题，保留历史。如服务实际拒绝下一步，记录该操作的当次错误，继续与它无关的制作。若首次独立运行确实缺少授权，说明对象和用途，只请求这项权限，等待期间不启动 Player。
