# 图片职责与读取范围

本文件维护证据要求、图号、来源与交接选择；几何／字体／两态参数由[UI布局](play-ui-layout.md)维护，纸艺／配色由[系列视觉](series-visual.md)维护。

## 设计前局内图

2026-11-11用户原话：“以后所有文档在设计时，都事先做好局内图片给我看。”适用于本技能设计的玩法开发文档：新文档，以及会改变玩法呈现、交互或布局的重设计，必须先制作并在对话中直接展示本玩法的局内效果图，再完成正文与飞书交付。可以先整理生成图片所需的规则、数值和布局；不能先交付完整文档，再把图片留到用户追问时补做。仅文字校对且画面不变时可沿用并展示现有有效局内图，无需重画。

- 至少展示一张完整横屏正常游玩状态，包含本玩法真实对象、合法示例状态、说明、倒计时及比分；按玩法需要补关键状态，不能拿原作截图、系列主题模板或只有文字的线框充数。栅格效果图使用可用的图像生成能力，并实际检查数字、状态、文字、分栏、留白与多余控件。
- 图号使用本玩法专属V1等，与原作证据G图、系列参考R图区分。图注标明“局内设计效果图”，示例数值不改变计分或生成规则；不标为实机截图、运行资产或用户已认可。
- 已确定的现行视觉和交互规格仍有效。生成图不能覆盖精确坐标、原背景复用或尺寸公式；发现偏差先修正，不能将生成错误写成新需求。
- 生图时明确各区域可用边界、主体包围盒与留白值，按[区域边界与等量留白](series-visual.md#区域边界与等量留白)保证游玩主体上下空白充足且相等；删除提示文字后重新计算布局，不能沿用旧图的偏下或贴边位置。
- 用户提供反馈时先修图及相关规则，再成稿；展示本身不等于用户认可，也不自行增加必须等待确认的审批关口。用户明确要求先确认时按其要求等待。
- 定稿采用的局内图放在本玩法输入包内，美术/UI章节引用，并与同版飞书正文一起交付；不放进系列公共图库。仅请求单独预览图时直接展示，不因此自动重写既有文档。

## 玩法证据 G 系列

有原游戏/视频时，在文档前部核心玩法旁给可点击原链接（含分P/集数）、标题与片段时间范围。实际观看后截取能解释“操作前→动作/判定→结果”的关键画面，通常2–4张；不以相似静帧凑数，不用生成图伪造原视频帧。

每图注明G编号、时间点、可见事实、借鉴机制与本版改动。保留主体和必要上下文，原截图说明写在图注；截图是玩法证据，不是美术目标，不能用R图替代。单帧不能证明速度、计分或隐藏输入。视频不可访问时说明未核对项与自主设计；仅有图片的输入按原图设计，不强求或编造视频。

G图、原链接、时间点与图注随同版飞书正文和Markdown ZIP交付；每款游戏的证据只存该游戏输入包，不堆进系列Skill图库。

## 随文交接

每份新稿附R15原文件、选定的一张R22–R25及实际使用的组件参考；不用四套候选或历史图塞满输入包。图注写明“固定原资产”或“已认可设计参考”，正文展开所选主题及精确布局，不能只写图号或本机路径。带UI参考不能直接用作运行底图。
