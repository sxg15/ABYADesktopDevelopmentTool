## 任务模板入口

主入口为同级 ../abya-game-development-task/SKILL.md，本模板只补充多人约束。
用户明确指定本模板即视为已选择，不重复询问、不递归调用入口。
沿用公共流程的需求、计划、交付三个确认点和任务资料，不另建一套阶段或十二轮。
局部联机修复只处理请求范围；已有有效检查与 Bot 报告直接引用，变化后复验影响部分。


# ABYA 多人游戏制作流程

目标是交付打开后即可验证的最新多人游戏。以用户最新明确要求及手动编辑的数据为准；保留不涉及本次修改的规则、美术和数据。用户要求实现时，完成实现、原生存档应用和验证，不停在设计或本地构建。

## 1. 确定本次玩法契约

从当前项目和对话提取下表；沿用提问模式，允许提问时只问影响实现且不能推断的空缺，不追问时将关键未知写进待确认需求。已确定的选择不重复确认，建议与已确认规则分开记录。

| 决策 | 需要明确的内容 |
|---|---|
| 参与方式 | 人数范围、系统 Player 或无 Player、竞技或协作、加入和退出方式 |
| 核心循环 | 输入、有效操作、成功与失败、阶段推进、撤销和重开是否适用 |
| 比赛规则 | 开始条件、是否限时、计分、同分、结束与截止瞬间的判定 |
| 公平策略 | 同内容同顺序、等难独立内容或共享场景；随机性与版本如何一致 |
| 设备与表现 | PC/手机、横竖屏、各玩家所见、公共信息、美术及动态效果要求 |
| 内容来源 | 手工数据、生成器或混合；数据格式、约束、备用内容与版本 |
| 交付范围 | 目标存档、当前源码、待保留的未保存内容、可玩的实例及验收指标 |

具体人数、时长、计分方式、交互载体、移动机制、场景规模、流程推进和难度曲线都必须来自当前任务，不作为通用默认。用户没有要求的提示、答案推荐、计时和生命值不要自行加入。个人身份与设备类型分离，手机不默认是控制器，PC 不默认是主持人。

## 2. 接入项目并建立架构

在 ABYA 环境中遵循当前可用的项目技能和 Runtime 文档：绑定当前开发会话，使用桌面托管实例，启动后先读取实例使用说明及真实 API。不要沿用旧任务的 GUID、端口、事件 ID 或接口猜测。已有实施授权继续有效，不为每一步重复请求许可。

先确认存档、关卡、实例模式及脏状态。保留未保存内容，不为测试擅自丢弃或保存无关修改。按环境要求维护计划和活动里程碑；工具缺失时说明能力缺口，不伪造工具执行。

将职责分开：

- 服务端或权威主机：参与者、比赛阶段、权威时间、规则判定、计分、结果和重置。
- 玩家对象或 Prefab：本人玩法状态与行为；验证对象归属、权威端及远端代理。
- 本地视图与输入：显示本人状态和公共信息，提交操作意图，不自行裁定最终得分。
- 共享规则与内容模块：客户端、服务端及验证器采用一致的规则与版本。

无系统 Player 的 ABYA 游戏按平台要求使用 Manual 模式，通过 FreeObject、CustomUI 和显式输入实现。不要将所有实体行为堆进全局逐帧遍历。修改玩法前，按当前架构接口取得快照并校验完整 manifest；要求 ready=true，修复错误，警告仅可用具体证据记录例外。按精确对象/Prefab 事件 scaffold、验证脚本，再使用原生绑定接口写入。

涉及同步、随机公平性及对局流程时读取 [联机与验收](references/network-and-acceptance.md)。

需求涉及人机时，读取同 provider 的公共 [人机开发指南](../abya-game-development-task/references/bot-development.md)。
沿用已确定的需求与授权，规划共用动作协议、观察握手、难度和接受证据，保留未涉及的旧定义。
上面的写前 ready 门槛对新 Bot 采用该指南的有限候选暂存例外：先检查基础架构和候选 Lua，
仅可撤销地暂存定义，重新取快照并通过完整 Bot 架构校验后再改玩法绑定；通过最终 lint 才保存。

## 2A. 现有素材与美术交接

沿用已有素材和风格；需要新选择时把候选或无模板方案纳入执行计划一起确认。
comic-arcade-ui 可作为适用候选，不作为多人任务自动默认。不再单独发起美术确认菜单。

选中后才读该模板和参考图，复用合适素材；它不改变玩法规则。文本自由物体与 CustomUI
仍使用 **DingTalk**，优先于风格建议。缺必要素材、字体或已选模板时在计划阶段提出，
不默认生成全套美术，不使用未经确认的占位资源。后续迭代沿用已确认选择。

## 3. 先打通完整对局，再扩展内容

以最小真实玩法打通：加入 → 准备 → 开始 → 操作 → 成功/失败 → 结束 → 再来一局。每个阶段写清可操作项、状态变化及下一阶段，不只制作一个可交互首页。

先证明两个独立身份能操作各自对象并共享正确结果，再扩大内容规模、增加复杂动画和装饰。多人规模按目标人数扩展验证，不能把两个客户端通过当作所有人数均已通过。

## 4. 内容数据化与发布

让外部编辑的文件成为明确的内容源，写清路径、字段、编码、编辑规则和导入命令。校验用户最新文件，再生成游戏可读内容；不要用旧缓存覆盖外部修改。

数据修改必须走完“源文件 → 校验 → 构建 → 原生目标绑定 → 保存 → 读回 → 新实例确认”。本地构建成功不等于实例已更新。详细执行 [数据导入与存档发布](references/data-and-release.md)。

## 5. 多端 UI 与美术

凡涉及字体设置，文本自由物体和自定义 UI（CustomUI）的文本都必须使用 **DingTalk** 字体。通过当前实例的资源与字体接口查找并设置实际的 DingTalk 字体引用，不使用默认字体或其他字体代替。设置后读回相关对象和 UI 节点的字体引用，确认 DingTalk 已实际应用；若字体资源不存在或接口无法设置，明确报告缺口，不将字体要求标记为完成。

主玩法区优先，公共状态与个人状态分清；布局随设备重排，不能重置玩法。按用户选定的视觉风格制作并实际导入资源，不能只生成素材文件。横屏不简单缩小竖屏坐标；手机优先完整显示主要内容，触控入口至少 44×44 逻辑像素并避开安全区。

使用九宫格时，实际配置图片边界、切片模式及按钮各状态资源：四角不拉伸，边沿按轴拉伸，中间区域填充。不要把图标、角色或整个复杂画面作为九宫格背景拉伸。检查小尺寸、长文字、禁用、按下及菜单展开状态，避免圆角、边框和布局接缝破损。

美术变体由内容种子稳定决定，不在每次重绘时重新随机。静态元素不逐帧重复设置；动画不改变规则碰撞或遮住操作区域。支持降低动态效果时保留必要操作反馈。

准备和结算保留必要操作。静态玩法说明与求解提示分离；当用户移除提示时，同时清除按钮、快捷键、菜单、推荐高亮和客户端答案反馈入口，内部验证器按需保留。

## 6. 性能分析与修复

出现掉帧时先建立可重复基线，再做隔离实验；不要根据直觉直接归因于引擎。读取 [性能分析与修复](references/performance.md)，保留测量条件、帧时间分布、受控变量及证据边界。

修复需要同时通过性能复测与玩法回归。静态 UI 达到高帧率不代表完整游戏已经修复，降低同步频率也不能破坏倒计时截止或计分准确性。

## 7. 真实联机验收与交付

保存并读回实现内容，完成要求的架构 lint。重新启动加载该存档的托管 Host 和独立 Client，验证不同身份、同一比赛及正确版本；编辑器本地预览不能代替联机证据。

按 [联机与验收](references/network-and-acceptance.md) 执行与变更相关的检查。界面变更提供真实横竖屏截图；性能变更提供同条件前后数据；数据变更提供实际条数、版本及运行实例的加载证据。不要用截图代替状态断言，也不要把静态校验说成真人试玩。
人机变更还须执行公共指南中的候选/验收检查，提供实际报名、动作接受、结算及双端清理证据。

交付说明包括：完成内容、实际存档/数据位置、测试拓扑和结果、已知限制、如何启动最新版本。用户要求亲自测试时，留下可见且可操作的正确实例，停止本次自动输入；仅清理本任务的临时资源。不因工具超时就反复覆盖写入，先读回检查是否已经生效，再决定有限重试或报告阻塞。
