# 制作阶段

用于完整玩法、较大改动或用户指定的独立阶段。只执行本次范围；完整任务按下列顺序推进。
读取任务已有资料，从未完成处接续，旧任务先映射已有成果，不补造确认、轮次或证据。
记录格式和模板见 [任务资料](production-records.md)，不用把全部模板作为必读文档。

## 1. 需求 → 确认需求文档

开局确认需求提问模式：允许提问，或不做需求追问。已有明确选择直接沿用。
读取用户资料，核定核心循环、胜负/重开、范围、设备、输入、页面/状态、素材和验收标准。
先读 playerMode。明确的单人/多人决定直接沿用；截图栏目、游戏分类及模板不能代替用户决定。
允许提问而人数未明确时，先在 APP 问答面板给出单人/多人选择，再按需敲定联网、协作或对抗。
多人不直接等于联网。系统 Player 或自由物体、Bot 等普通技术选择按需求给出建议。
业务问题通过 production update 的 publish-questions 发布（格式见任务资料），然后结束当前轮等待。
不要为需求问答调用原生终端问卷，不循环轮询或睡眠等答案。策划使用“提交并继续”，APP 会在当前轮次结束后按需续接；不要要求额外输入“继续”或先暂停。
若本轮结束前已读取到新提交答案，可以直接继续必要的需求梳理；已有下一组问题或待确认文档时明确等待对应用户操作，不重复发布。
恢复时读 questionGroups 的最新已提交答案，并 configure 记录用户明确的人数模式。
不追问时不发布问题，把建议默认值和关键未知写进需求文档，经原有文档确认敲定。
核心规则矛盾不能靠猜测消除；在待确认文档中说明并停住依赖该决定的工作。

需要任务模板时只看当前 provider 下 abya-task-template-* 的有效 marker 摘要。
marker 须为 schemaVersion=1、kind=abya-task-template、目录同名 id，具备 displayName、
description、sourceSkillName 和 SKILL.md。普通 Skill 和导入器不参与选择。
明确选择直接沿用；否则将建议模板或“无模板”纳入需求文档一起确认，不另开强制菜单。
未确认前不按建议模板写游戏；选中后才读正文。模板缺失或无效写为缺口，不静默替换。
需求文档用稳定 REQ 编号关联验收项，区分确认事实、建议和未知，并列出已有内容保留范围。
等待用户确认该文档版本，或记录已明确涵盖该版本内容的既有确认。

## 2. 资源整理〔完整美术生产暂缓〕

沿用现有素材、用户资源和已选美术模板。记录目标视口、风格、字体、页面及必要反馈。
美术模板只查 abya-art-template-* 的有效 abya-art-template.json 摘要，验证与任务模板
相同的身份字段、对应 kind 和 SKILL.md。已有明确风格不重问；建议风格纳入执行计划。
没有要求时不自动选 comic-arcade-ui；模板选择不等于授权新的素材生产或额外玩法。
仅加载实际选用的参考图及资源，检查能否导入、应用和满足设备要求。
缺必要素材列入计划阻塞；不自行使用未确认的占位物，不默认生成全部美术。
本阶段不增加人工确认节点；改变需求范围则更新受影响的需求版本。

## 3. 学习、选型与预检 → 确认执行计划

按需求查现有知识、模板、公开 Lua API 和资产，比较复用、组合和新增实现的理由。
按照 [运行与实现](runtime-authoring.md) 做必要的只读托管实例预检，不改玩法内容。
核对实际 Player/CLI、存档/关卡、工具 schema、资源、字体、测试拓扑与取证能力。
必要工具、素材、环境或完整过程录制能力缺失时，列明证据和恢复条件并暂停受影响阶段。
源码存在不证明当前 Player 可用；玩法任务不因此获得修改平台或扩大工具权限的授权。

计划对应 REQ 编号，写清职责分解、采用方案、批次、资源、测试、运行版本和恢复办法。
包含既有素材/美术模板选择与必要敏感操作的具体影响。用户确认计划版本后才写玩法。
只读环境检查可继续，不因普通内部实现选择再次请求批准。

## 4. Lua 实现 → 完整初版 R0

按 [运行与实现](runtime-authoring.md) 校验、实现、绑定、保存并读回。
内部先打通真实完整循环，再补齐确认范围；R0 必须可从进入自然运行到结果和重开。
每批将完成情况、缺陷、后续重点检查点写入任务记录，关联需求、条件和证据。
记录实际采用的知识/素材版本及落点；搜索、下载或计划采用不算已采用。
确认的内容与素材必须已实际应用；R0 不能是留待验收补齐核心内容的白模。
冻结 R0 的存档/构建标识、完整循环录像、页面/状态截图，再进入整体迭代。

## 5. 8＋4 迭代

读取 [整体迭代](whole-experience-review.md)，执行 R1—R12，不按维度拆分轮次。
当前轮次或证据缺失就记录缺失，不把旧对话中的“已做完”补写成测试结果。

## 6. 交付候选 → 用户验收

交付实际存档入口、对应版本、试玩步骤、范围结果、报告和未测项。
停止自动输入，留下正确且可操作的任务实例供策划试玩。
用户反馈是缺陷则修复并复验，是新需求则更新受影响的需求与计划。
确认只适用于对应作品版本；影响行为的新修改需要重新验证和确认。
自检通过、检查器通过和用户认可分别记录，未获用户认可不更改任务完成状态。

## 7. 收尾与知识分析

核对正式资源和依赖、来源、必要维护文件与证据，整理保留项及具体后续问题。
仅在已授权范围清理本任务暂存，先检查归属和消费者，优先可恢复处理；不清理共用资源。
归纳项目经验、公共知识候选、Skill 建议、工具缺口。实际采用与公共发布分开。
缺口区分文档、用法/模板、API能力、旧运行包、工具故障、取证工具、实现错误与待查证。
公共 Skill/APA 知识发布另走其审核边界；本步骤不自动发布、不增加固定迭代轮数。
